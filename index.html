NebulaForge Handbook

version 1.0 — last edited by hand, not on a schedule

This is the documentation for NebulaForge, a Linux system built from source starting from an existing LFS install. It covers what's actually in the system, how the package manager works, and a couple of things that broke badly enough that I didn't want to forget how I fixed them.

It is not a tutorial and it is not trying to sell you anything. If you're not the person who built this, most of it probably won't apply to your hardware.

Chapter 1. Introduction

1.1.What this is

NebulaForge is a source-based Linux system. Almost everything on it was built from a tarball with make, cmake, or a hand-written build script, the same way LFS itself is built. There's no package repository and no binary packages. If you want software on it, you compile it.

1.2.Where it came from

It's a copy of an already-working LFS install. Same kernel, same toolchain. I imaged the original system and kept experimenting on the copy so I wouldn't wreck the one I'd already spent time on. The original is still on its own partition, unchanged.

It has since become its own thing: own partition, own GRUB entry, own kernel it boots without a chroot. /etc/os-release reports it as NebulaForge Linux 1.0. The hostname still says lfs. I haven't fixed that.

Chapter 2. Orbital

2.1.Why it exists

Typing ./configure && make && make install by hand for every package gets old. Orbital is a small Python script that does three things: downloads a source tarball, builds it, and remembers what got installed so it can be removed later. That's the whole scope.

2.2.Recipe format

A recipe is a Python file. Most of them don't need real code — if the project builds with make, cmake, or autotools, this is the entire recipe:

name = "btop"
version = "1.4.7"
source_url = "https://github.com/aristocratos/btop/archive/refs/tags/v1.4.7.tar.gz"
sha256 = None
dependencies = []
build_system = "make"

Orbital fills in the actual build and install commands from the build_system line. Projects that don't fit that pattern — Firefox's own build tool, cargo, meson — get a short build() and install() function instead. That's the only escape hatch, and it's used maybe a dozen times across the whole recipe set.

2.3.Commands

commanddoes
orbital install NAMEfetch, build, install
orbital remove NAMEuninstall using the recorded file list
orbital listeverything currently installed
orbital info NAMEversion, file count, size on disk, missing files
orbital resumepick a crashed or interrupted install back up
orbital search TERMcheck local recipes and the built-in list
orbital edit-recipe NAMEopen a recipe, or a blank template, in $EDITOR
note orbital resume reuses whatever was already downloaded and extracted. It doesn't start a build over from nothing. This mattered once, during a kernel-module build, more than I expected it to.

2.4.Limits

There's no dependency resolver worth the name — it walks a flat list, it doesn't solve version conflicts. There's no signing, no binary packages, no mirrors. The built-in list of zero-config packages is small because every entry in it got added by hand, one at a time, when I happened to want that package. It is not trying to be apt or pacman. It's trying to be less typing than doing it manually.

Chapter 3. The desktop

bspwm, sxhkd, polybar, picom, kitty. A common combination, not an original one. Colors are adapted from a rice called Emilia, which is itself a Tokyo Night palette — dark navy background, muted purple and blue borders.

bspc config normal_border_color   "#414868"
bspc config focused_border_color  "#bb9af7"
bspc config presel_feedback_color "#583794"

picom runs for transparency and shadows. kitty sits at 85% opacity. polybar shows workspaces, the clock, and CPU/memory, and nothing else — I didn't add modules I wasn't going to look at.

neofetch's ASCII art is a Saturn rendering instead of the default logo, found on an old ASCII-art archive with no listed author.

Chapter 4. The Nvidia driver problem

This chapter exists so I don't have to solve this twice. Getting Nvidia's driver to build against a hand-built kernel took several wrong turns before the real problem showed up.

4.1.Renamed kernel functions

The build failed on sys_close, which doesn't exist in this kernel version anymore. Patched it to ksys_close. That didn't exist either — the real name in this kernel is close_fd, found by grepping the actual kernel headers instead of trusting a forum post. Same thing happened with del_timer_sync, which is now timer_delete_sync, in two separate files.

4.2.The actual problem

With every rename fixed, the build failed at the link stage with pages of undefined-symbol errors for things as ordinary as memcpy. That's not a compatibility problem. That's a missing Module.symvers file, and it's only generated by a full kernel build. Every attempt up to that point had used the lighter make modules_prepare, which skips it. One full make -j$(nproc) later, the file existed, and the driver linked without complaint.

note The renamed functions were real. They also weren't the actual issue — every patch before the full kernel build was necessary and none of them were sufficient on their own.

Moving the working driver to the second machine was simpler: copy the five resulting .ko files and the userspace libraries over, run depmod for the right kernel version, run nvidia-xconfig. No patching needed a second time.

Chapter 6. Installing on a fresh machine

There's no installer program and there isn't going to be one. NebulaForge is source-based on purpose — the whole point of running something like this is deciding for yourself what goes on the machine, not answering a wizard's questions and getting whatever it decided to give you. What follows is the manual process, the same one used to put NebulaForge on its own partition in the first place. Every command in this chapter has actually been run.

note This gets you a booting base system with a network connection and a compiler. Everything past that — desktop, drivers, anything else in this handbook — is Chapter 2 through 5 done again by hand, or copied over from an existing install. Nothing here decides that for you.

6.1.What you need first

A machine, a second working Linux system to build the target from (any live USB will do — Gentoo, Void, Arch, whatever's on hand), and the base tarball:

tar --numeric-owner --xattrs -cJf nebulaforge-base.tar.xz \
  --exclude='./proc/*' --exclude='./sys/*' --exclude='./dev/*' \
  --exclude='./tmp/*'  --exclude='./run/*' \
  -C /path/to/nebulaforge .

That's the command that makes the tarball in the first place, run from a system that already has NebulaForge on it. If you're the one installing rather than the one producing the tarball, you just need the resulting file.

6.2.Partition the disk

However you want. This is not prescriptive — one partition, an existing layout with room made for one more, LVM, whatever suits the machine. The only requirement is a partition big enough for the base system (currently around 6 GB compressed, more once it's extracted and you've built anything on top of it) formatted as something Linux can boot from:

mkfs.ext4 -L NEBULAFORGE /dev/sdXN

Replace /dev/sdXN with the actual partition. Check with lsblk first. Confirm it twice. This step doesn't ask again.

6.3.Extract the base system

mkdir -p /mnt/target
mount /dev/sdXN /mnt/target
tar --numeric-owner --xattrs -xJf nebulaforge-base.tar.xz -C /mnt/target

That's the entire install step. Everything that makes NebulaForge what it is — Orbital, the toolchain, whatever recipes existed at tarball time — is now sitting on the new partition.

6.4.Chroot in and fix the basics

The tarball doesn't know what disk it landed on, so a couple of things need correcting before it'll boot on its own.

mount --bind /dev  /mnt/target/dev
mount --bind /proc /mnt/target/proc
mount --bind /sys  /mnt/target/sys
mount --bind /dev/pts /mnt/target/dev/pts
cp /etc/resolv.conf /mnt/target/etc/resolv.conf
chroot /mnt/target /bin/bash
source /etc/profile

Inside the chroot, find the new partition's UUID and put it in /etc/fstab:

blkid /dev/sdXN
sed -i 's/UUID=OLD-UUID-HERE/UUID=YOUR-NEW-UUID/' /etc/fstab

The old UUID in the tarball's fstab belongs to the machine it was built on. It has to be replaced or the system won't mount its own root on boot.

6.5.Bootloader

If the machine already runs GRUB for something else, os-prober will usually find the new install on its own:

grub-mkconfig -o /boot/grub/grub.cfg

Check the generated entry before trusting it — specifically the root= line the kernel gets booted with. If os-prober picked up a stale root device from somewhere else on the disk, it'll be wrong, and the fix is a plain text edit to that one line in grub.cfg. This happened once already; it's not rare.

If there's no existing bootloader at all, install one from inside the chroot the normal way for whatever hardware this is (BIOS or UEFI). That part isn't NebulaForge-specific and isn't covered here.

6.6.Everything after that is up to you

At this point there's a bootable machine with a base toolchain, Orbital, and whatever recipes were in /etc/orbital/recipes at the moment the tarball was made — no desktop, no drivers, no assumptions. What goes on top is Chapters 2 through 5 of this handbook, done again by hand, or skipped entirely in favor of something else. That's the actual point of building it this way.
